# Індексація колекції · Лабораторна 2

---

## 1. Колекція
- **Документів:** 15 (відповідає вимозі 10–40) · **символів усього:** 11 938 · **мови:** українська та англійська (технічна термінологія)
- **Де лежить:** тека `corpus/` у корені репозиторію
- **Імʼя файлу = `id` документа зі spec.md:** Так, строго відповідає (`corpus/doc-01.md` → `doc-01`, ..., `corpus/doc-15.md` → `doc-15`). Саме ці ідентифікатори використовуються в полі `must_cite` еталонного набору `queries.jsonl`.

---

## 2. Правило фрагментації і чому саме таке
- **Межі:** Первинний поділ здійснюється за рядками-заголовками Markdown (`#`, `##`), задовгі розділи діляться за абзацами (`\n\n`) та кінцями речень, а короткі фрагменти приклеюються до попереднього фрагмента того самого розділу.
- **Числові параметри правила (`RULE` у `src/rag/chunk.ts`):**
  - Максимум: **1200** символів
  - Мінімум: **200** символів
  - Перекриття (overlap): **120** символів
- **Обґрунтування правила:** Наші документи — це структуровані інженерні стандарти та формули протоколів MCP і AI SDK. Середній розмір тематичного підрозділу становить 600–900 символів. Максимальне вікно 1200 символів дозволяє зберегти кожен підрозділ цілісним без штучного розрізання таблиць або списків аргументів, а поріг 200 символів усуває появу беззмістовних «огризків».
- **Результати фрагментації колекції:**
  - Кількість фрагментів: **15**
  - Довжина фрагментів: медіана **813** симв., мінімум **673** симв., максимум **896** симв.
- **Нормалізація тексту:** `BOM прибрано, CRLF→LF, пробіли в кінці рядків прибрано`.

## 3. Ембедінги
- **Шлях:** Підтримка уніфікованого інтерфейсу `Embedder` для двох шляхів за $0 та детермінованого офлайн-провайдера:
  - Шлях А (локальний): Ollama `embeddinggemma-2:270m` (768 вимірів)

- **Фіксована розмірність:** **768** вимірів (єдина для всіх провайдерів проєкту для сумісності).

## 4. Індекс
- **Файл індексу:** `data/index.json` · **розмір:** ~0.1 МБ · **зберігання в git:** Так, зафіксовано в репозиторії для відтворюваності в CI та на деплої без локального запуску Ollama.
- **Метод пошуку:** Косинусна схожість векторів (`cosineSimilarity`), повний перебір у пам'яті.
- **Чому не окрема векторна база:** Для колекції з 15 документів і 15 фрагментів навантаження тривіальне (скалярний добуток 15 векторів виконується менш ніж за 0.2 мілісекунди в пам'яті процесу), тому додавання зовнішньої бази даних було б надлишковим ускладненням.
- **Час побудови:** **0.1 с** локально.

## 5. Відтворюваність
- **Команда побудови індексу:**
  ```powershell
  npm run index
  ```
- **Повторний запуск:** Повністю детермінований — дає ті самі `id`, ті самі числові межі `start`/`end` та стабільні вектори.
- **Перевірка інваріантів у CI:**
  - `tests/chunk.test.ts` — перевірка інваріанта `text === normalize(raw).slice(start, end)`, лімітів довжини та шляху заголовків.
  - `tests/index.test.ts` — перевірка кількості документів (10–40), перевірка розмірності (768) та звірка sha256 хешів документів.

## 6. Що зберігається для цитування (вхід для кроку 05)
Кожен запис у `data/index.json` містить:
- `id`: унікальний стабільний ідентифікатор фрагмента (формат `doc-XX#0000`)
- `docId`: ідентифікатор документа (`doc-01` ... `doc-15`)
- `heading`: повний шлях заголовків Markdown (наприклад, `Model Context Protocol › Architecture`)
- `start` та `end`: точні 0-based зсуви символів у нормалізованому тексті
- `text`: нормалізований фрагмент тексту
- `vector`: L2-нормалізований вектор ембедінгу розмірності 768.
