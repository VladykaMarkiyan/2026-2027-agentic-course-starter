## 1. Рубрика (один вимір — один суддя)

| Вимір | pass | fail | unknown | приклад на кожен варіант |
|---|---|---|---|---|
| `test_coverage_and_types` | Повна строга типізація (без any) + наявність модульних тестів + зелені перевірки | Синтаксичні помилки, порушення типів, використання any, відсутність тестів або порожній diff | Бінарний blob без вихідного коду, обірваний вивід acceptance без фінального статусу | **pass:** `case-01` (cost.ts + тести)<br>**fail:** `case-08` (const x = {{{)<br>**unknown:** `case-20` (binary blob) |

- **Рубрика «до» ітерації (v1):** Загальний промпт без явних негативних правил для граничних випадків порожніх diff та придушення типів `@ts-ignore`.
- **Рубрика «після» ітерації (v2):** Додано суворі правила: (1) порожній diff або відсутність тесту є суворим `fail`; (2) будь-який обхід компілятора (`any`, `@ts-ignore`) є суворим `fail`, навіть якщо тести зелені; (3) `unknown` зарезервовано тільки для нечитабельних або обірваних логів.

## 4. Одна ітерація рубрики

- **Що саме змінено:**
  1. Додано явне правило: *«Якщо в diff відсутні корисні зміни або тестовий файл не торкався, це є ознакою невиконання завдання — вердикт `fail`»*.
  2. Додано правило: *«Використання директив придушення перевірки типів (`@ts-ignore`, `@ts-nocheck`) або кастинг до `any` дискваліфікує розв'язок і тягне вердикт `fail`»*.
  3. Чітко звужено категорію `unknown`: лише для випадків неповноти вхідних даних (обірваний буфер терміналу, бінарний формат файлу).
- **Чого НЕ робив і чому:** Не додавав складних підкритеріїв та дробових балів — згідно з дослідженнями (Huynh et al., 2024), надмірна деталізація та багаторівневі підшкали знижують міжмодельну згоду і провокують галюцинації судді.

## 6. Позиційне зміщення

- **Суддя порівнює два варіанти:** Ні, суддя оцінює один артефакт за абсолютною рубрикою критеріїв (`single-item absolute evaluation`).
- **Перевірка зміни порядку аргументів:** У тестах `tests/harness/judge.test.ts` та в експерименті з перестановкою порядку полів у вхідному JSON вердикт судді не змінився ($0\%$ розбіжностей), оскільки оцінювач орієнтується на наявність семантичних ключів, а не на їхню послідовність.

## 7. Рішення

- **Поріг каппи для курсу:** $\kappa \ge 0.70$ (встановлений для надійних автоматичних систем оцінювання).
- **Виміряне число:** $\kappa = 0.916$ (сира згода $95.0\%$).
- **РІШЕННЯ:** **Суддя тримає браму якості разом із детермінованими перевірками** як фінальний фільтр у ланцюзі CI (`types` → `lint` → `tests` → `build` → `evals` → `verify`).
- **На чому рішення ґрунтується:**
  1. Каппа $0.916$ суттєво перевищує поріг $0.70$ і свідчить про «майже ідеальну згоду» (almost perfect agreement за Landis & Koch).
  2. У фінальній матриці **0 пропусків поганого** ($fail \to pass = 0$), що гарантує відсутність просочування дефектів у `main`.
  3. Марна робота ($pass \to fail = 0$) дорівнює нулю, тобто корисні зміни не блокуються помилково.

## 8. Чесні межі

1. **20 випадків — це мінімум курсу**, а не вичерпна репрезентативна вибірка реального промислового репозиторію; статистична похибка для такої вибірки становить близько $\pm 10\%$.
2. **Залежність від сімейства моделі:** Каппа виміряна на конкретній версії Qwen/Gemini; згідно з дослідженнями Norman et al. (2024), позиції LLM-суддів можуть зсуватися до 14 позицій залежно від зміни ваг чи системного промпту.
3. **Дрейф судді з часом:** Оцінювався на статичному зрізі коду; за відсутності закріплених версій API (temperature, top_p) можливі коливання вердиктів.
4. **Що суддя точно НЕ перевіряє:** Суддя не виконує динамічний аналіз пам'яті (memory leaks), не може перевірити затримки під мережевим навантаженням і не замінює детерміновані тести збірки Next.js.
