# Автоматичне зупинення: бюджет, таймаут, circuit breaker — Лабораторна 3

## 1. Три шари зупинення

| Шар | Що обмежує | Чим реалізовано | Значення за замовчуванням | Де в коді |
|---|---|---|---|---|
| **задача** | ходи агента | `maxTurns` / `--max-turns` (неінтерактивний режим `-p`) | 10 ходів | `scripts/harness/run-task.ts` |
| **задача** | бюджет у $ | `maxBudgetUsd` / `--max-budget-usd` (клієнтська оцінка) | $0.40 на задачу | `scripts/harness/run-task.ts` |
| **задача** | час виконання | таймаут процесу `timeout_s` у `spawnSync` | 300 с (5 хв) | `scripts/harness/run-task.ts` |
| **прогін** | кроки циклу | `stopWhen: [isStepCount(N), hasToolCall(...)]` | `maxSteps = 5` | `src/agent/agent-loop.ts`, `src/agent/agent-aisdk.ts` |
| **CI** | час ранера | `timeout-minutes` задач і окремих кроків | 5–15 хв | `.github/workflows/gates.yml` |
| **харнес** | повтор аварій | Circuit Breaker (`closed` / `open` / `half-open`) | поріг 3 аварії, 15 хв cooldown | `scripts/harness/circuit-breaker.ts` |

Типові значення, які діяли б без мого контролю:
- `ToolLoopAgent` у AI SDK — `isStepCount(20)`;
- Базовий `generateText` / `streamText` — `isStepCount(1)`;
- `WorkflowAgent` — без ліміту кроків (небезпечно для автономних циклів).

## 2. Circuit Breaker

- **Умови спрацювання (тригери):**
  1. $N = 3$ однакових аварій або відмов підряд (`exitCode !== 0` або провал `acceptance`).
  2. Вичерпання бюджету моделі (`Budget limit reached` або перевищення `max_usd`).
  3. Відмова провайдера за лімітами квот (HTTP 429 / Rate Limit Exceeded).
- **Час перепочинку (cooldown):** 15 хвилин паузи перед наступною спробою.
- **Стан Half-open:** Після завершення часу охолодження дозволяється **рівно одна пробна задача**:
  - якщо вона успішна → стан повертається у `closed`, а лічильник аварій скидається на 0;
  - якщо вона зазнає невдачі → стан негайно повертається в `open` з новим періодом охолодження.
- **Де живе стан між прогонами:** `.harness/breaker.json` (в CI передається через GitHub Actions artifact `breaker`).

## 3. Походження патерну — чесно

*Martin Fowler, «CircuitBreaker» (06.03.2014):* класичний патерн архітектури розподілених систем, що використовує кінцевий автомат зі станами `closed`, `open` та `half-open` для захисту від каскадних відмов зовнішніх сервісів.  
Первинного вендорського джерела, яке б стандартизувало брейкер саме для агентних кодуючих циклів, наразі немає. Це інженерне рішення, адаптоване за аналогією для запобігання спалюванню коштів, квот API та безкоштовних хвилин CI.

## 4. Прогін, який зупинився сам

- **Прогін:** `docs/lab3/runs/t-03-1794321114991/`
- **Який ліміт спрацював:** Ліміт вичерпання бюджету агента (`budget_or_turns`).
- **На чому саме:** Задача `t-03` черги, агент зупинився через досягнення бюджетної стелі (`Budget limit reached (intentional stop test)`).
- **Що харнес зробив далі:**
  1. Виконавець перехопив статус виходу і класифікував його як `budget_or_turns` (а не звичайне падіння процесу `agent_failed`).
  2. Зафіксував причину та час у `run.json` і `docs/lab3/stop-log.jsonl`.
  3. Передав результат у `recordTaskResult()`, запобігши подальшим безконтрольним запускам черги.
- **Чи це те, що планувалося:** Так, агент не продовжував крутитися в циклі, зупинив витрату ресурсів і залишив деталізований лог.
- **Рядок журналу:** Зафіксовано у `docs/lab3/stop-log.jsonl`.

## 5. Чого я НЕ контролюю

- `maxBudgetUsd` — це клієнтська оцінка вартості токенів, яка може мати відхилення від точного білінгу провайдера (закладається 20% запас).
- Витрати, відновлені з продовженої сесії (`--resume`), не входять у ліміт нового прогону.
- Витрати субагентів входять у сумарний ліміт сесії: при досягненні порогу нові субагенти блокуються, а фонові примусово завершуються.
- На безкоштовному шляху (Ollama / Gemini Free) грошові ліміти не діють, тому ключовими захисними механізмами є таймаут процесу `timeout_s` та Circuit Breaker харнеса.
